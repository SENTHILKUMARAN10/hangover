# Hangover Shakes — QR table ordering and kitchen display

**This is IN-CAFE DINE-IN ordering only.** There is no WhatsApp ordering, delivery checkout, online pickup, card payment, required phone number or customer account. Keep the original marketing site while showing an Add to Cart and checkout only when the URL contains a valid table number (`/?table=01`). Each table has a separate printed QR card from `table-qr.html`. The guest selects items/variants and quantities and optionally gives a name and special instructions. The guest sends the request; the authorised kitchen receives a large table-number ticket and works through **received → accepted → preparing → ready → served** (or declined). The guest can follow statuses while their browser remains open; staff bring the food to the table. Staff handle the bill directly.

**Important security limitation:** QR codes are public table identifiers, not location verification. Someone can share a link or edit `?table=01` to impersonate a table. A customer with a QR URL can still submit remotely. For a production location-only guarantee, a server-based on-site validation method and server-enforced rate limits are required. In the current no-orders-database model the kitchen MUST check that the table is occupied before accepting. Do not claim this system technically blocks distant customers.

## Complete these steps BEFORE enabling the order button

1. Ask the café for the **verified email address of the authorised kitchen tablet/owner account**. Never use the website developer's email unless the café explicitly designates that account. Do not ask for, store or publish passwords, OTPs, access tokens or secret keys.
2. Create a **new dedicated café-owned Supabase project** solely for staff email authentication and private ephemeral Realtime channels. Do not use anyone's unrelated projects and do not create an orders table. This realtime service is a message transport; it is still an external backend service, just not a persistent order database.
3. In `supabase-realtime-policies.sql`, replace EVERY `kitchen@example.com` with the actual verified kitchen account email; apply to the dedicated project only. In Supabase Realtime settings, turn OFF **Allow public access**. Review/remove any other broader policies on these topics. The SQL creates separate guest send-only and staff read-only permissions for order requests; guests cannot read the whole kitchen inbox or impersonate kitchen presence or status messages.
4. Enable Supabase email-link authentication, arrange the approved staff account, and set Auth **Site URL** and allowed **Redirect URLs** to the final `https://www.hangovershakes.cafe/admin.html` (and any real alternate origin actually in use). Staff sign in from this page with their own email link. The public `admin.html` URL is deliberately `noindex`, but security comes from Auth + Realtime RLS, not hiding its URL.
5. Edit `ordering-config.js`: provide only the project's **public URL** and **publishable key**. Never put a service-role/secret key, JWT signing secret, owner password or API token in browser code. `tableCount` defaults to 30. Change the table count in BOTH `ordering-config.js` and the `table-qr.html`/`table-qr.js` generator if the café has more than 30 tables.
6. Deploy the complete repository to the existing host for `www.hangovershakes.cafe` without altering the friend's domain/DNS hosting configuration. Confirm HTTPS works and the latest CSS, images, menu, `ordering.js`, `admin.html`, `table-qr.html`, and scripts load. Avoid accidentally deploying the older clone instead of the latest `main` branch.
7. Open `/table-qr.html` in a browser with internet, generate the actual table range, print the cards, and CHECK every QR on a separate phone. The code must open the real production website, show the right table and display the full menu. Attach it physically to the corresponding table. `table-qr.html` is a publicly accessible print tool (the QR contains no secrets); you may remove the generator from production after printing if the café prefers.
8. **Mandatory two-device end-to-end test:** Staff open `/admin.html` and authenticate on a kitchen tablet; screen displays LIVE and stays awake. On a separate phone, scan Table 01, add a single-price item and a two-price variant, confirm its table/cart/subtotal, and send a test order. Verify kitchen ticket shows Table 01, items and trustworthy menu prices. Verify receipt, accept, preparing, ready, served reach the customer's phone. Repeat Table 02, guest with no name, notes including special characters, invalid/reused table parameters, declines, invalid payload, wrong staff email, kitchen offline, network disconnect and a refresh. Check 320px and 375px mobile layouts and QR scan quality. **Do not accept actual customer orders until this test passes.**
9. Train staff to check physical occupancy, confirm menu stock/pricing, monitor the kitchen display, turn off screen sleep, and keep a manual fallback when the tablet or internet fails. Place a visible table notice saying an order is not accepted until the kitchen acknowledges it.

## Deliberate limitations

- **No database/order history.** The kitchen queue exists only in the open browser's memory. Refresh, lost connectivity, browser sleep or server restart can lose orders or statuses. Guests should not retry uncertain orders without asking staff; duplicates are possible. There is no guaranteed notification or offline recovery. If the café needs trustworthy operational ordering, use a durable, access-controlled backend and idempotency keys.
- The customer basket is saved only in that customer's browser and separated by table number. Names, notes and kitchen orders are not written to browser localStorage or an app orders table. Supabase Realtime is still used for transient message delivery and owner authentication.
- Authentication and RLS protect the kitchen inbox; **the customer QR is NOT a verified on-site session**. Browser Wi-Fi checks, GPS, secret URL claims or merely hiding the QR do not reliably guarantee physical presence. Staff must approve each request; use server-side on-site validation and abuse controls for a strict location-only system.
- Guests can submit spam with a known public table URL. Static frontend validation is not server-side rate limiting. The kitchen accepts/declines before cooking; recommend adding server-enforced anti-abuse and on-site credentials for production.
- Only the current order's recent status is displayed prominently on the guest phone; orders are not recoverable after refresh. The kitchen must verify total, offers/discounts, taxes, availability and billing before serving. Cart subtotal is not a tax invoice.

## Local automated checks

Run `node tests/ordering-contract.test.cjs` and `node --check ordering.js && node --check admin.js && node --check table-qr.js`. GitHub Actions performs syntax and static contracts on each push. A green build does NOT mean an end-to-end live order or physical-location restriction was tested.
